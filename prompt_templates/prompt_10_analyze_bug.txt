# TASK
Phân tích bug report, log lỗi, hoặc bằng chứng test fail từ cổng PARSCA Vendor ({FE_URL}/vendor) và API ({API_URL}) theo quy trình Fact -> Root Cause -> Recommendation.
Nạp trước: kit-test-parsca/GEMINI.md, .agent/rules/core.md, .agent/skills/analyze-bug/SKILL.md, .agent/workflows/analyze-bug.md.

# CONTEXT
- Hệ thống: PARSCA Marketplace (FE SPA + BE NestJS REST API)
- Tài liệu BA tham chiếu: docs/parsca-vendor-test-docs/ (00–20)
- Danh mục module: .agent/skills/generate-testcase/resources/module_catalog.md
- Mã bug chuẩn: BUG-PARSCA-<MOD>-<YYYYMMDD>-<NN> (ví dụ: BUG-PARSCA-CSV-20261020-01)

Thông tin lỗi cần phân tích:
[DÁN MÔ TẢ LỖI, BẰNG CHỨNG, LOG MẠNG, TRACE PLAYWRIGHT HOẶC SCREENSHOT VÀO ĐÂY]
Ví dụ:
Mô tả: Vendor V1 nhập mã sản phẩm của Vendor V2 vào URL chi tiết /vendor/products/:idV2 thì màn hình hiển thị toàn bộ thông tin sản phẩm của V2 thay vì chặn lại.
Request/Response: GET /products/admin/:idV2 trả về status 200 OK với body dữ liệu của V2.

# CONSTRAINTS
Phân loại lỗi theo cây quyết định 5 nhóm đặc trưng của PARSCA:
1. Environment: Do lệch prefix /v1, bọc {data, meta}, hoặc BE sập -> Báo đội DevOps/Dev, không ghi bug riêng từng màn hình.
2. Observation: Hành vi trên màn [GIẢ LẬP] (Dashboard, Orders, Reviews, Payouts, Settings, Profile trừ avatar) -> Không ghi bug "không gọi API / không lưu dữ liệu".
3. Question PO: Hành vi thuộc nhãn THEO CODE HIỆN TẠI (như vendor nhập được Rating, Q-V2, Q-V4, Q-V5, Q-V8...) -> Soạn câu hỏi PO mã Q-Vx, ghi trạng thái OBSERVED, không tính là bug hay pass.
4. Not a bug: Bộ lọc thời gian tương đối ở Orders/Reviews trả kết quả rỗng do ngày hệ thống là tháng 10/2026 trong khi dữ liệu mẫu là tháng 05-08/2026.
5. Test issue: Do locator lỗi, timeout Playwright, hết hạn token 15 phút, hoặc rate limit 5 lần/phút.
6. Real Bug: Lỗi logic thực sự, vi phạm Business Rules (BR-01 đến BR-12) hoặc tài liệu BA.

Nguyên tắc an toàn & bảo mật:
- Tuyệt đối KHÔNG in credentials thật, token, cookie, hoặc dữ liệu nhạy cảm ra báo cáo.
